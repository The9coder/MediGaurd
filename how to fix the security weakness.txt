How to Fix the Security Weaknesses in MediGuard

This project is intentionally vulnerable for educational purposes. The following remediation steps are the most important fixes to make it safer and closer to production quality.

1) Remove hardcoded secrets and use environment-based configuration

Problem:
- Secrets are stored directly in source code in app/config.py.
- This includes default JWT secret keys and a fake internal API key.

Fix:
- Move all secrets to environment variables or a secure secret manager (AWS Secrets Manager, Azure Key Vault, HashiCorp Vault, Docker secrets, or equivalent).
- Example:
  - JWT_SECRET
  - SECRET_KEY
  - DB_PASSWORD
  - INTERNAL_API_KEY
- Load them at runtime and fail fast if they are missing in production.
- Do not commit secrets to Git.
- Add a .env.example file with placeholders instead of real values.

Example:
  export JWT_SECRET="replace-with-real-secret"
  export DB_PASSWORD="replace-with-real-db-password"

2) Use parameterized queries everywhere to prevent SQL injection

Problem:
- Dynamic SQL is built using string concatenation in patients routes.
- This creates injection risks if unsanitized input reaches the SQL statement.

Fix:
- Use parameterized SQL with placeholders and pass values as parameters.
- Avoid constructing SQL statements with user-controlled text.
- Keep query structure fixed and values bound separately.

Example:
  cursor.execute(
      "SELECT * FROM patients WHERE id = %s AND assigned_to = %s",
      (patient_id, username),
  )

- Review all SQL statements for any use of f-strings or string concatenation.

3) Remove verbose error messages and stack traces from API responses

Problem:
- app/factory.py returns raw traceback and internal exception details to clients.
- This leaks internal implementation details and helps attackers craft targeted exploits.

Fix:
- Log the traceback server-side only.
- Return a generic error message to the client, such as:
  {"error": "Internal server error"}
- Use proper error logging with structured logs.
- In production, do not expose file names, library versions, or stack traces via HTTP responses.

Example:
  @app.errorhandler(500)
  def internal_error(error):
      app.logger.exception("Unhandled exception")
      return jsonify({"error": "Internal server error"}), 500

4) Add rate limiting and lockout for authentication attempts

Problem:
- Login endpoints accept weak credentials and do not limit repeated failed attempts.
- Attackers can brute-force user accounts.

Fix:
- Add login throttling per IP and per username.
- Lock accounts temporarily after repeated failed attempts.
- Log suspicious login activity to a security monitoring system.
- Use MFA for admin and privileged accounts.
- Avoid exposing whether the username exists or whether the password is wrong in a way that helps attackers enumerate users.

Example protections:
- 5 failed attempts = 15-minute temporary lockout
- 10 failed attempts = manual review / alerting
- Rate limiting middleware or Flask-Limiter

5) Upgrade vulnerable dependencies

Problem:
- requirements.txt pins older Flask, Werkzeug, and Jinja versions with known CVEs.

Fix:
- Update to supported, patched versions.
- Run dependency scanning regularly with tools such as:
  - pip-audit
  - safety
  - Dependabot
  - GitHub security alerts
- Rebuild and redeploy containers after updates.

6) Improve JWT validation and session handling

Problem:
- Defaults in app/config.py are weak and not suitable for production.
- JWT uses secret values from source and may not be protected with proper rotation and validation.

Fix:
- Use strong random secrets and rotate them.
- Validate token content thoroughly.
- Enforce short access tokens and refresh tokens when needed.
- Store tokens appropriately and avoid accepting expired or malformed tokens.
- Add proper logout/revocation if tokens are used beyond basic demo behavior.

7) Validate all inputs and enforce least privilege

Problem:
- Some API data is not strictly validated or role-scoped.
- The app should ensure users can only access their own patient records unless they are admin.

Fix:
- Validate all request payloads carefully.
- Enforce strict schema checks.
- Use RBAC (role-based access control) consistently.
- Confirm admin-only operations are restricted to admin roles.
- Apply principle of least privilege to database accounts and services.

8) Harden the app configuration for production

Problem:
- The project is configured like a local development demo.

Fix:
- Disable debug mode in production.
- Set secure cookie attributes where applicable.
- Add security headers such as Content-Security-Policy, X-Frame-Options, and Referrer-Policy.
- Run behind HTTPS only.
- Use secure database connections and encrypted storage for data at rest and in transit.
- Enable WAF or reverse proxy protections when deployed.

9) Add automated security checks to CI/CD

Problem:
- The repo includes security gates in CI, but they are meant to catch issues after the fact.

Fix:
- Ensure these automated checks run on every commit and pull request:
  - Bandit (SAST)
  - pip-audit / safety (dependency scanning)
  - detect-secrets / gitleaks (secret scanning)
  - pytest with coverage enforcement
  - linting (flake8 / black)
  - DAST checks such as OWASP ZAP
- Fail the build when any critical issue is found.

10) Use secure logging and monitoring

Problem:
- Logs are useful for detection, but they should not leak sensitive details.

Fix:
- Log without exposing secrets, internal stack traces, or patient data.
- Store logs in secure locations with access restrictions.
- Monitor for failed login bursts, injection attempts, abnormal record access, and privilege abuse.
- Integrate with SIEM or detection tools for alerts.

Recommended fix order

1. Remove hardcoded secrets
2. Fix SQL injection vectors
3. Block stack trace exposure
4. Add brute-force protection and rate limiting
5. Upgrade vulnerable packages
6. Add production security hardening
7. Add CI/CD security gates and security monitoring

Final note

This repo is a controlled vulnerability lab. Real production systems should not retain these weaknesses. The safest path is to turn the project into a secure-by-default application, then run automated security scanning before every release.

If you want an even more concrete remediation plan, the next step would be to update the code in the following order:
- app/config.py
- app/routes/patients.py
- app/factory.py
- app/routes/auth.py
- requirements.txt
- CI workflow and security checks
