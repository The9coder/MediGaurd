MediGuard Security Status and Production Readiness Notes

This repository is a prototype and must not be treated as a production-ready healthcare system. It has not been independently audited, assessed for DPDP compliance, clinically validated, or reviewed for applicable medical-device obligations. Do not use real patient data or clinical predictions until those reviews are complete.

Security controls implemented in this write

1. Authentication and sessions
- Local username/password registration and demo accounts were removed.
- The portal uses an OIDC authorization-code flow through a configured identity provider.
- The identity provider must enforce MFA and manage account activation, deactivation, and role membership.
- Application sessions are stored server-side in Redis; browser storage contains no access token.
- Production uses Secure, HttpOnly, SameSite cookies with a short session lifetime.
- OIDC callback state is validated by Authlib.
- State-changing browser requests require a CSRF token.

2. Patient data access
- Patient ownership uses the OIDC subject identifier, not a user-supplied owner.
- Routes apply subject-scoped queries and PostgreSQL row-level security provides an additional boundary.
- Admin access is granted only when the configured signed OIDC role claim contains the configured admin role.
- Patient creation and prediction features are schema/range checked.

3. Database and audit controls
- Persistence is PostgreSQL; runtime schema creation has been removed.
- The intended app role receives SELECT/INSERT on patient and prediction data.
- Audit events contain action and resource metadata only, not patient names, diagnoses, or prediction inputs.
- Audit rows are INSERT-only for the runtime role and committed with the operation.
- Production PostgreSQL connections must use TLS.
- Production deployments still need managed encryption at rest, encrypted backups, monitoring, migration controls, and verified role grants/RLS.

4. Application and deployment hardening
- Generic 500 and database-unavailable responses do not disclose internals.
- Security headers, request-size limits, no-store responses, and endpoint-only access logging are enabled.
- Rate limiting uses shared Redis storage rather than process-local counters.
- The container runs as non-root, read-only, with dropped Linux capabilities and no direct public bind by default.
- Secrets are explicit deployment inputs; no sample secret is a valid production credential.

5. Prediction safety gate
- Predictions are disabled by default in production.
- Enabling them requires a pinned model SHA-256 and a validation-reference identifier.
- A hash only establishes artifact integrity. It does not establish that a model is safe, clinically accurate, unbiased, calibrated, or approved.
- The current sample model is not validated for Indian patients and must not inform diagnosis or treatment.

Remaining work before real-data use

1. Obtain an independent security review and resolve findings; perform threat modeling and penetration testing.
2. Have qualified counsel assess the DPDP Act/rules, lawful basis, notices, retention/deletion, processors, breach handling, and cross-border transfers.
3. Have clinical and regulatory specialists validate the intended use, populations, model performance, calibration, bias, usability, monitoring, fallback, and applicable CDSCO/medical-device requirements.
4. Configure and test a production OIDC provider with MFA, role governance, deprovisioning, recovery, and session revocation.
5. Deploy managed PostgreSQL and Redis with TLS, private network access, encryption at rest, secret rotation, restricted operator access, encrypted backups, and tested restoration.
6. Apply PostgreSQL schema changes using a privileged migration identity. Confirm the runtime role is not an owner or BYPASSRLS role and cannot update/delete audit rows.
7. Configure trusted ingress/TLS, monitoring, audit retention, incident response, alerting, and controlled access to logs.
8. Add and enforce CI checks for tests, SAST, dependency scanning, secret scanning, container scanning, and DAST.

The Docker Compose stack is a local integration example only. It uses non-TLS internal service connections and does not supply managed storage encryption, deployment identity management, production backups, monitoring, or regulatory controls. Never use it as-is for real health information.
